# Generate Challenge

Turn the current conversation into a shortlist of high-originality Capability Challenges. The deliverable is a set of challenge concepts ready for selection—not generated artifacts, model calls, experiments, or execution plans in progress.

## Non-negotiable gates

Every proposed challenge must pass both gates:

1. **Publicly obtainable input** — All required inputs must be generated by the agent or obtainable from the open web without logging in, such as public code repositories, public websites, open datasets, documentation, or public social-media posts. Reject concepts that depend on authenticated SaaS access, private or real-user data, confidential material, unpublished customer cases, or any input that cannot be independently retrieved from the public internet.
2. **Meaningful output** — The result must provide practical, educational, analytical, creative, or reusable value. Boundary tests are welcome, but reject concepts whose main purpose is spectacle, outrage, novelty without insight, or engagement bait.

Treat these as hard eligibility requirements, not merely ranking preferences.

## 1. Recover the brief

Extract from the conversation:

- target model, product, release, or capability;
- modality: image, video, audio, LLM, coding agent, multimodal, or other;
- intended audience and account positioning;
- desired tone: boundary-pushing, useful, playful, visual, or mixed;
- available public inputs, tools, budget, time, and publishing format;
- how each input can be generated or retrieved without authentication, and what useful purpose the output serves;
- any ideas already discussed, so they are not proposed again as if new.

If one missing fact would materially change the candidates, ask only the smallest necessary question and stop. Otherwise state concise assumptions and continue.

**Completion criterion:** the brief is specific enough to reject candidates that are off-topic, infeasible, visually weak, redundant, dependent on non-public inputs, or lacking meaningful output value.

## 2. Check the frontier

For a current release or trend, inspect the official announcement/capability documentation and search recent X discussion when tools are available. Identify:

- what is genuinely new;
- the capability boundaries worth probing;
- demos and challenges that are already saturated;
- constraints that make a result interpretable;
- public, reproducible input sources suitable for the challenge.

This is a novelty check, not a general research report. Prefer primary sources. Never invent product capabilities or popularity signals.

Skip external research when the conversation already supplies sufficient, current facts or the challenge is intentionally product-agnostic.

**Completion criterion:** every proposed challenge is compatible with the target and is not merely a renamed version of an obvious launch demo.

## 3. Generate a diverse slate

Generate 8 candidates by default. Vary the underlying challenge, not just the wording. Unless the brief calls for a narrower slate, cover a useful mix of:

- a hard boundary or constraint-compliance challenge;
- a real production task with an unusually demanding brief;
- a visually immediate result;
- a playful challenge that still produces a useful or instructive result;
- a continuity, causality, consistency, or multi-step challenge where applicable;
- a challenge whose failure is as interesting as success;
- a cross-modal or model-relay challenge where it adds real value;
- a format that can become a repeatable series for future model releases.

A strong challenge has:

1. **One legible question** — viewers understand what is being tested immediately.
2. **A visible artifact** — the output itself can carry the post without an operation recording.
3. **Productive tension** — success, partial success, and failure all produce something worth discussing.
4. **Specific constraints** — enough structure to distinguish capability from luck or taste.
5. **Topical fit** — it uses what is interesting about this model or moment.
6. **Originality** — it is not a generic “make a game,” “draw hands,” tool list, or official-demo imitation.
7. **Feasibility** — one person or a later execution agent can run it with the stated resources.
8. **Input accessibility** — every input has a concrete, login-free acquisition path from agent generation or the public web.
9. **Output value** — the artifact teaches something, solves or illustrates a real problem, supports a decision, or can be reused beyond the post itself.

Do not claim that a playful challenge is a scientific benchmark. Do not preselect only outcomes that would support a desired conclusion. Do not use private, sensitive, real-user, or inaccessible case data even if anonymization seems possible. Do not propose pure engagement bait; reach can be a benefit, but it cannot be the challenge's sole value.

**Completion criterion:** no two candidates test the same core question, every candidate uses independently obtainable public inputs, and each produces meaningful value and remains worth publishing under at least two plausible outcomes.

## 4. Specify each candidate

Use this compact structure for every candidate:

```markdown
## N. Challenge title

**Hook:** One sentence suitable for the opening of an X post.

**Challenge:** The exact task and its important constraints.

**Input source:** The specific agent-generated or public, login-free input and how it can be retrieved.

**Boundary:** What capability or failure mode this probes.

**Artifact:** What the audience will see in the final post/video.

**Value:** The practical, educational, analytical, creative, or reusable benefit of the output.

**Why it may spread:** The surprise, utility, conflict, or visual payoff, treated as secondary to value.

**Outcome branches:** What would be interesting about success, partial success, and failure.

**Execution needs:** Required access, inputs, approximate runs, and obvious cost/time risks.

**Series potential:** How this could be reused for later models, or `one-off`.
```

Include an exact prompt draft only when it clarifies the concept. Treat it as a draft for the later execution stage, not as an instruction to run now. Write explanatory text in the user's language; write model prompts in the language most suitable for the target unless the brief says otherwise.

## 5. Rank without collapsing diversity

End with a decision table:

| Candidate | Originality | Visual payoff | Boundary value | Input accessibility | Output value | Feasibility | Topicality | Best for |
|---|---:|---:|---:|---:|---:|---:|---:|---|

Score each dimension from 1–5. Exclude rather than rank any candidate that fails either non-negotiable gate. Then recommend:

- **Best overall**;
- **Best for reach**;
- **Best for credibility**;
- **Cheapest fast test**.

Recommendations may point to the same candidate only when the scores genuinely justify it. Explain each choice in one sentence.

Finish by asking the user to choose a candidate or request one refinement axis. Do not begin executing, generating media, calling the target model, creating test fixtures, or implementing automation.

**Completion criterion:** the user can select one challenge without needing another round merely to understand what public input it uses, what would be produced, or why the output is worth attempting.
